这篇不是方法论，纯粹记录一次真实改造。

我们的团队同时在用 Codex 和 Lark。白天在电脑前，很多分析和代码相关的问题都在 Codex 里走；离开工位以后，大家会在 Lark 里继续问同一件事。刚开始我觉得这很正常，后来发现有点不对：同一个 defect，在两个入口里像两条平行线。

有一次挺典型。Lark 里问“DEF-123 最后结论是什么”，系统给了另一条任务的摘要；我回到 Codex 继续问，得到的又是另一版上下文。结果就是早会里同一件事讲了三遍。那一刻我才确认，这不是提示词问题，也不是某个模型抽风，而是我们没有真正做“统一记忆”。

## 我们先走错了一步

第一反应当然是同步聊天记录。实现也不复杂，看起来像捷径。  
但这个方案只在 demo 阶段好看，进入真实协作就开始变形：聊天内容噪声太大、线程会跳、同义表达太多，而且 IM 渠道本来就更宽，一不小心就会把不该露的细节露出去。

所以后面我把目标改了，从“同步消息”改成“同步任务状态”。这两个说法差别不大，实际工作量差很多，但方向是对的。

## 后来怎么改

正确做法其实很直接：不要同步聊天，而是建一个平台侧的共享 memory 服务，专门管理结构化、带作用域（scoped）的任务状态。Codex 和 Lark 都只跟这个服务读写。  
换句话说，统一记忆不再是“哪边消息多就信哪边”，而是“同一个任务状态在两个入口复用”。

这个服务里我只让结构化摘要跨端流动，不直接暴露原始聊天。每条记录至少带上 `user_id`、`project_id`、`task_id`、`channel`、`timestamp`、`permission_scope`，检索主键按 `user + project + task + artifact` 组织。只按 `user_id` 检索迟早串线，这点在我们项目里已经验证过了。

三层记忆（Conversation / Working / Long-Term）我也做了，但那更多是实现细节。这里真正决定成败的，是“共享 memory 服务 + 结构化状态 + scope 约束”这三个点。

还有一个很实操但常被忽略的点：歧义不要猜。  
Lark 上经常有人只问一句“上次那个结论呢”。我的处理顺序是先看显式信息（DEF 编号、项目名），再看线程上下文，再看最近活跃任务。如果还不够，就追问。宁可多问一句，也别自信地答错一句。

## 最小架构与落地顺序

![最小架构与落地顺序](/images/2026-03-06-unified-memory-codex-lark/min-architecture.svg)
*Codex 与 Lark 统一记忆的最小架构与落地顺序*

架构上我们没有搞复杂，就是两个入口（Codex、Lark）都只走同一个 Memory API，再把 workflow、artifact、索引、权限服务挂在后面。  
落地顺序也很朴素：先做 Working Memory 的最小闭环，再强制写入字段，再收敛 Lark 返回格式（摘要+链接+下一步），然后补歧义追问，最后加任务收尾摘要。这里顺序挺重要，尤其前两步，少一步后面都会返工。

## 现在还没解决完的部分

这套方案到现在为止是有效的，但离“完成”还差得远。  
首先是维护成本，Memory API 和权限策略不是一次性工作；其次是摘要质量，它会直接影响检索质量；再就是时效性，任务状态变得很快时，摘要会有短时间滞后。

接下来我主要补三件事：摘要质量评估与回放（低质量自动重写）、关键任务人工确认点、以及 Lark 端的来源标注（明确来自哪个 task/artifact）。做完这些，统一记忆至少是一个可追溯、可恢复、可以慢慢变好的工程系统，而不是“看起来打通了”的演示系统。
