# 这个问题是怎么暴露出来的

我所在的项目同时使用 Codex 和 Lark：在电脑前主要通过 Codex 做研发分析，在通勤或开会间隙会用 Lark 继续追问任务细节。真正让我意识到问题严重的是跨端切换时的断层：在 Lark 里已经聊过的结论，回到 Codex 还要重讲；在 Codex 里刚完成的分析，到 Lark 里又像“没发生过”。随着并行任务变多，这种断层会直接变成错误检索，同一个人同时跟进多个项目和多个 defect 时，问一句“上次结论是什么”，很容易拿到别的任务答案。

# 我比较过的两条路线

最直觉的路线是同步 Codex 与 Lark 的聊天记录。它短期看起来见效快，但很快暴露出三个问题：聊天内容噪声太高、跨线程语义会串线、IM 渠道的权限边界不清晰。另一条路线是把记忆上收为平台能力，让 Codex 和 Lark 都只通过统一 Memory API 读写。这条路前期成本更高，需要统一数据结构和权限策略，但治理能力明显更强。最后我选了第二条，目标也从“消息同步”改成“任务状态连续”。

# 我最后怎么把方案落下来

## 先把记忆分层，而不是一锅端

我把统一记忆拆成三层：Conversation Memory 负责线程内短期连贯，Working Memory 负责跨端共享的任务状态，Long-Term Memory 负责沉淀可复用的稳定信息。实际落地里，真正支撑跨端连续性的主层是 Working Memory，因为它可以直接承载结论、置信度、下一步动作和关联 artifact，而不是一大段原始对话。

## 再把作用域从“人”扩展到“任务”

只按用户检索很快会串线，所以我把主键思路固定为 `user + project + task + artifact`。写入时至少带上 `user_id`、`project_id`、`task_id`、`channel`、`timestamp` 和 `permission_scope`，这样在 Lark 里问到“上次缺陷结论”时，系统才能先收敛到正确任务，再返回答案。

## 歧义不猜测，按顺序消解

用户经常不会把上下文说完整，所以我的检索链路会先看显式信息（比如 DEF 编号和项目名），再看线程和频道上下文，再按近期活跃任务做候选排序。如果候选仍不唯一，就直接追问确认，而不是静默猜一个“最像的答案”。

## 共享摘要，保留日志；同任务不同端不同可见性

原始日志我会保留用于审计，但跨端默认共享的是结构化摘要。这样内容更稳定，也更容易在不同端展示。同一任务在不同渠道会做可见性分层：Codex 可以看到更细节的信息，Lark 默认只返回摘要、关键结论和跳转链接。

## 最小架构与落地顺序

![最小架构与落地顺序](/images/2026-03-06-unified-memory-codex-lark/min-architecture.svg)
*Codex 与 Lark 统一记忆的最小架构与落地顺序*

落地节奏上，我先做了一个 2-4 周 MVP：第一步只做 Working Memory，不碰全量历史同步；第二步把写入字段标准化，强制带 `user_id + project_id + task_id`；第三步把 Lark 端响应收敛为“摘要 + 链接 + 下一步”；第四步把低置信度追问接进检索链路；最后在任务收尾时自动写入结构化总结。

# 这套方案的代价与下一步

这条路线把跨端连续性问题解决了，但代价也很明确：需要长期维护 Memory API、索引和权限策略，复杂度明显高于“消息转发”；摘要质量会直接影响检索质量；任务状态变化快时，摘要和真实进度之间也可能出现短时不一致。

下一步我会优先做三件事：先补摘要质量评估和回放机制，低质量摘要自动重写；再给关键任务加人工确认点，避免错误状态扩散；最后在 Lark 端补充“上下文来源说明”，让每条回答都能追溯到具体 task 和 artifact。到这一步，统一记忆就不只是“记住内容”，而是具备可审计、可恢复、可持续迭代的工程能力。
